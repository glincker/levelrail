## levelrail-cli migrate

Subcommands: agent, caprover, checklist, coolify, cutover, db-copy, db-status, dokploy, hub, plan, server, status, step, volumes

```
Usage:
  levelrail-cli migrate coolify --url URL --token TOKEN [flags]    migrate apps from a Coolify instance
  levelrail-cli migrate dokploy --url URL --token TOKEN [flags]    migrate apps from a Dokploy instance
  levelrail-cli migrate caprover --url URL --token TOKEN [flags]   migrate apps from a CapRover instance
  levelrail-cli migrate verify <coolify|dokploy|caprover> --url URL --token TOKEN
                                                           parity report against the source before cutover (exit 1 on a blocking difference)

  levelrail-cli migrate [coolify|dokploy|caprover|server] --resume JOB [--retry] [--follow] [--retire [--probe] [--ack STEP]]
                                                           resume a migration job: status, retry failures, safe-to-delete check

Database migration hub and cutover checklists:
  levelrail-cli migrate hub sessions <list|show|select|step|apply|receipt|connection|reveal|delete>
  levelrail-cli migrate checklist <list|show|step>

Data and cutover steps, after "import platform":
  levelrail-cli migrate server --engine postgres --host H --user U --list|--plan|--apply   migrate every database of a source server, read-only on the source
  levelrail-cli migrate db-copy NAME --host H --user U --database D   copy live data into an imported database and verify row counts
  levelrail-cli migrate db-status [NAME]                              per-database copy status
  levelrail-cli migrate volumes --source user@host                    print the commands that copy imported volumes
  levelrail-cli migrate cutover [--verify]                            go or no-go for the DNS switch, then verify after it
  levelrail-cli migrate plan --url U --token T [--apply --only ID]    read-only plan with a verdict per item, then import chosen items
  levelrail-cli migrate status [APP]                                  cutover checklist per migrated app
  levelrail-cli migrate step APP STEP [--reset]                       complete or reopen a checklist step
  levelrail-cli migrate agent start|status|verify|reopen|remove       read-only agent on the old server (discovery and volume compare)

The source database password is read from APP_MIGRATE_SOURCE_DB_PASSWORD or --password-stdin.

Run "levelrail-cli migrate <source> -h" for a source's own flags.
```

## levelrail-cli migrate agent

Subcommands: remove, reopen, start, status, verify

```
Usage:
  levelrail-cli migrate agent start [--label L] [--control-plane-addr HOST:PORT]   create a single-use token and print the install command
  levelrail-cli migrate agent status [SESSION]                                     sessions, or one session with what the agent found
  levelrail-cli migrate agent verify SESSION APP [--target NAME=FILES:BYTES]       compare the app's volumes with the source; zero diffs complete data_verified
  levelrail-cli migrate agent reopen APP                                           undo the agent's data_verified (also reopens the steps after it)
  levelrail-cli migrate agent remove SESSION                                       revoke the session now; works even if the source host is unreachable

The agent is read only and never moves data in this release: it lists what runs on the source and
compares file counts and sizes. Databases are not dumped or counted by it.
```

## levelrail-cli migrate checklist

Subcommands: list, show, step

```
Usage:
  levelrail-cli migrate checklist list [flags]               every imported app's cutover progress
  levelrail-cli migrate checklist show <app> [flags]         one app's steps
  levelrail-cli migrate checklist step <app> <step> --done|--reset [--note TEXT] [--confirm]
                                                    [--database NAME] [--volume NAME=SF:SB:TF:TB] [flags]

Steps: imported, data_verified, shadow_running, dns_switched, old_stopped. --reset reopens the step and every step after it.
Completing a step needs write:sensitive.
```

## levelrail-cli migrate coolify

Subcommands: resume, undo

```
Usage:
  levelrail-cli migrate coolify --url URL --token TOKEN [flags]
  levelrail-cli migrate coolify resume --journal FILE --url URL --token TOKEN [flags]
  levelrail-cli migrate coolify undo --journal FILE [--dry-run] [--yes] [--force] [--include-data]

One-way migration from a live Coolify instance to Levelrail. Default
mode writes app.yaml files plus a migration report; --apply creates apps
directly on a target Levelrail instance instead of writing files.

Flags:
  --url string                     Coolify instance base URL, e.g. https://coolify.example.com (required)
  --token string                   Coolify API bearer token (required)
  --stage-dir string              directory for staged one-click services, default ./migrated/compose (written in both modes, never deployed)
  --domain-suffix string      parent domain for staged service hosts, default localhost
  --out-dir string                directory for generated files, default ./migrated (file mode only)
  --apply                            create apps on the target Levelrail instance instead of writing files
  --dry-run                       print the exact plan, per-resource outcomes and cutover checklist; writes nothing
  --verify                         the same report from the target, so apps already imported show as imported
  --only string                   limit --dry-run and --verify to these app names or Coolify ids
  --insecure-tls                  skip TLS verification of Coolify (--dry-run and --verify, and the services read)
  --allow-private                 allow a private-network Coolify address
  --include-secret-values     fetch real env var values from Coolify (requires a Coolify token with the read:sensitive ability)
  --target-token string        Levelrail API token, --apply only (default: LEVELRAIL_TOKEN or APP_API_TOKEN env var, then the credentials file)
  --target-profile string      named credentials profile for the target Levelrail instance, --apply only
  --target-api-url string    Levelrail control plane base URL, --apply only (default: LEVELRAIL_API_URL or APP_API_URL env var, then http://localhost:8080)
  --json                             print the migration report as JSON to stdout, nothing else
  --node-map string               source-server=node pairs, comma-separated; --apply places each app on its node,
                                  an unmapped server stays on the control plane node, an unknown node is refused
  --create-webhooks                with --apply, register one push webhook per git-sourced app through the
                                  connected git provider for its host (default off, it writes to the git host);
                                  without --apply the report lists what would be created
  --journal string                with --apply, the apply journal to write (default under the config dir,
                                  printed at the end); resume reads it and continues the open steps
  --output string          output format: json, table, or text (default table; --json is shorthand for --output json)
  --query string           JMESPath expression to filter the result before printing
  -h, --help               show this help

One-click services are staged as <stage-dir>/<name>/compose.yaml with generated
secrets and the printed "compose deploy" command; unsupported keys are listed.

--dry-run and --verify cover what this command's file and --apply modes do
not: databases, volumes, scheduled tasks, webhooks, servers and a DNS
switch order. Stage them with "import apps --from coolify".

Every --apply run writes a journal of what it created, step by step (names
and step states only, never values or secrets). "resume" re-reads the
source with the same flags and finishes the open steps without re-creating
anything; apps that already existed are left alone. "undo" removes only
what the run created; see "levelrail-cli migrate coolify undo -h".

Git repo/branch identity is not persisted Levelrail state today: the
report prints the exact "apps create --repo ... --ref ..." follow-up
command for each migrated app that had one.
```

## levelrail-cli migrate dokploy

Subcommands: resume, undo

```
Usage:
  levelrail-cli migrate dokploy --url URL --token TOKEN [flags]
  levelrail-cli migrate dokploy resume --journal FILE --url URL --token TOKEN [flags]
  levelrail-cli migrate dokploy undo --journal FILE [--dry-run] [--yes] [--force] [--include-data]

One-way migration from a live Dokploy instance to Levelrail. Default
mode writes app.yaml files plus a migration report; --apply creates apps
directly on a target Levelrail instance instead of writing files.

Flags:
  --url string                     Dokploy instance base URL, e.g. https://dokploy.example.com (required)
  --token string                   Dokploy API key (required)
  --out-dir string                directory for generated files, default ./migrated (file mode only)
  --stage-dir string               directory compose stacks are staged into, default ./migrated/compose
  --apply                            create apps on the target Levelrail instance instead of writing files
  --include-secret-values     write real env var values already returned by Dokploy into a secrets file or apply them
  --target-token string        Levelrail API token, --apply only (default: LEVELRAIL_TOKEN or APP_API_TOKEN env var, then the credentials file)
  --target-profile string      named credentials profile for the target Levelrail instance, --apply only
  --target-api-url string    Levelrail control plane base URL, --apply only (default: LEVELRAIL_API_URL or APP_API_URL env var, then http://localhost:8080)
  --json                             print the migration report as JSON to stdout, nothing else
  --node-map string               source-server=node pairs, comma-separated; --apply places each app on its node,
                                  an unmapped server stays on the control plane node, an unknown node is refused
  --create-webhooks                with --apply, register one push webhook per git-sourced app through the
                                  connected git provider for its host (default off, it writes to the git host);
                                  without --apply the report lists what would be created
  --journal string                with --apply, the apply journal to write (default under the config dir,
                                  printed at the end); resume reads it and continues the open steps
  --enable-backup-schedules       keep imported database backup schedules running when they were on in
                                  Dokploy; by default they are imported paused
  --enable-imported-channels      create imported alert channels enabled; by default they are created
                                  disabled so nothing is sent until you turn them on; an enabled channel
                                  receives broadcast notices (key rotation reminders, maintenance and
                                  update notices) right away, with no routing needed
  --output string          output format: json, table, or text (default table; --json is shorthand for --output json)
  --query string           JMESPath expression to filter the result before printing
  -h, --help               show this help

Compose stacks are staged as compose apps (compose.yaml plus stack.env)
after the same validation a manual compose deploy runs; deploy each with
the printed compose deploy command.

Dokploy's docker (prebuilt image) and drop (file upload) source types,
and its nixpacks/heroku_buildpacks/paketo_buildpacks build types, have no
Levelrail equivalent and are reported for manual review, not migrated.

Object-storage backup destinations and database backup schedules are
imported too. A destination's keys are used only with --apply and
--include-secret-values, go straight to the backup target create call and
are never printed or journaled; otherwise the target is reported as
needs_secret with the create command to run. A name that already exists
is skipped, never overwritten. Schedules bind to the database of the same
name on the target and are imported paused unless
--enable-backup-schedules is given.

Notification providers become alert channels of the matching kind (slack,
discord, telegram, email, gotify, ntfy, lark, pushover; custom becomes
generic). Tokens and webhook URLs are read only with --apply and
--include-secret-values and go straight to the channel create call;
otherwise the channel is reported as needs_secret with a placeholder
command. Channels are created disabled unless --enable-imported-channels
is given, an existing name is skipped, and other kinds are listed as
unsupported.

Every --apply run writes a journal of what it created, step by step (names
and step states only, never values or secrets). "resume" re-reads the
source with the same flags and finishes the open steps without re-creating
anything; apps that already existed are left alone. "undo" removes only
what the run created; see "levelrail-cli migrate dokploy undo -h".

Git repo/branch identity is not persisted Levelrail state today: the
report prints the exact "apps create --repo ... --ref ..." follow-up
command for each migrated app that had one.
```

## levelrail-cli migrate hub

Subcommands: sessions

```
Usage:
  levelrail-cli migrate hub sessions list [flags]                     sessions, without their databases
  levelrail-cli migrate hub sessions show <id> [flags]                one session's databases, checks and progress
  levelrail-cli migrate hub sessions select <id> [--select DB] [--deselect DB] [--target-name DB=NAME] [--target-version DB=VER]
  levelrail-cli migrate hub sessions step <id> <inventory|preflight|verify|cutover> [flags]
  levelrail-cli migrate hub sessions apply <id> [--password-stdin] [--yes] [flags]  start copying the selected databases
  levelrail-cli migrate hub sessions receipt <id> [--out FILE [--force]] [flags]  the read-only receipt, secrets masked
  levelrail-cli migrate hub sessions connection <id> <db> [flags]       a verified database's connection, no secret
  levelrail-cli migrate hub sessions reveal <id> <db> [--yes] [flags]   the same with its password (read:sensitive, audited)
  levelrail-cli migrate hub sessions delete <id> [--yes] [flags]        drop a session and the password held for it

Selection and apply need write:sensitive. The source password is never a flag:
apply reuses the one held for the session, or reads one line with --password-stdin.
```
