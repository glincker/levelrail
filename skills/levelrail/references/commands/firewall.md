## levelrail-cli firewall

Subcommands: allow, delete, deny, exposure, ingress, list, restrict, unrestrict

```
Usage:
  levelrail-cli firewall status [flags]                                          show whether the host firewall (ufw) is on and which ports it needs
  levelrail-cli firewall enable [--dry-run] [flags]                              allow SSH, 80, 443 and the control plane ports, then turn ufw on
  levelrail-cli firewall disable [--dry-run] [flags]                             turn ufw off
  levelrail-cli firewall exposure [--node N] [--probe] [flags]                   audit which published container ports are reachable from outside
  levelrail-cli firewall restrict --port N --allow CIDR[,CIDR] --dry-run|--apply   limit a published port to an allow-list (DOCKER-USER)
  levelrail-cli firewall confirm --port N [flags]                                 keep a restriction that is waiting for confirmation
  levelrail-cli firewall unrestrict --port N [flags]                              remove a restriction Levelrail added
  levelrail-cli firewall list [flags]                                            list configured firewall rules
  levelrail-cli firewall allow --port N [--protocol tcp|udp] [--source-cidr CIDR] [--label TEXT] [flags]   add an allow rule
  levelrail-cli firewall deny --port N [--protocol tcp|udp] [--source-cidr CIDR] [--label TEXT] [flags]    add a deny rule
  levelrail-cli firewall delete <id> [flags]                                      remove a firewall rule
  levelrail-cli firewall ingress <subcommand>                                    web request firewall: rules, bans, bots, attack mode (run "levelrail-cli firewall ingress -h")

A deny rule, or an allow rule scoped to a source CIDR, targeting a port
this control plane itself needs (the management API, agent connections,
or ingress) is refused rather than applied.

Run "levelrail-cli firewall <subcommand> -h" for a subcommand's own flags.
```

## levelrail-cli firewall ingress

Subcommands: attack-mode, audit, bans, block, bots, bypass, rules, status, traffic

```
Usage:
  levelrail-cli firewall ingress status [--scope HOST] [--range 1h|6h|24h]
  levelrail-cli firewall ingress rules list
  levelrail-cli firewall ingress rules add --name N --action allow|deny|challenge|log|rate_limit --when "FIELD OP VALUE" [--when ...] [flags]
  levelrail-cli firewall ingress rules update <id> [same flags as add]
  levelrail-cli firewall ingress rules delete <id>
  levelrail-cli firewall ingress rules move <id> --to POSITION
  levelrail-cli firewall ingress block <ip-or-cidr> [--scope HOST] [--note TEXT] [--force]
  levelrail-cli firewall ingress bypass <ip-or-cidr> [--scope HOST] [--note TEXT]
  levelrail-cli firewall ingress bans list
  levelrail-cli firewall ingress bans lift <ip>
  levelrail-cli firewall ingress bots show
  levelrail-cli firewall ingress bots set [--bots off|log|challenge|block] [--ai-bots off|log|challenge|block] [--ai-agents a,b,c] [--bans on|off]
  levelrail-cli firewall ingress attack-mode on [--minutes N] [--challenge]
  levelrail-cli firewall ingress attack-mode off
  levelrail-cli firewall ingress traffic [--scope HOST]
  levelrail-cli firewall ingress audit [--limit N]

The ingress firewall filters web requests before they reach an app. It is
separate from the host firewall commands above, which manage ports on the
server itself. Rules run in order; allow ends evaluation, deny and challenge
end it, log and rate_limit let the request continue unless the limit trips.
A condition is FIELD OP VALUE, for example "path starts_with /admin",
"header:X-Env equals prod", "ip in_cidr 203.0.113.0/24" or "query:debug exists".
Fields: path host method header:NAME query:NAME user_agent ip country.
Operators: equals starts_with contains glob in_cidr exists.
```
