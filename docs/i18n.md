This page is for contributors to the dashboard. New user-facing strings go through i18n (`scripts/check-i18n.sh` fails a commit that adds literal JSX text to a file outside `t()`), English is the source language and Spanish (`es`) ships for the `common` namespace. Many older components still hardcode English: migrate a component when you touch it, and run `scripts/i18n-inventory.sh` to list the files with the most remaining literal strings.

The stack is `react-i18next` with `i18next`, in the plain Vite and React app. It gives you plain `t('key')` calls with no extraction step, namespace-based lazy loading, and typed keys.

## Where strings live

Translations are in `web/src/locales/<language>/<namespace>.json`. A namespace maps to a feature area, not to one component: `deploys.json` holds keys for several deploy-settings cards. The current namespaces are `common`, `deploys`, `settings`, `dashboard`, `auditLog`, `streams`, `networkProxy`, `databases`, `https` and `nodes`.

Nest keys by component inside the file, and name a key for what the string is for, not its English text:

```json
{
  "autoRollback": {
    "title": "Auto-rollback on crashloop",
    "enabledLabel": "Enabled",
    "toast": {
      "enabled": "Auto-rollback on crashloop enabled.",
      "errorTitle": "Could not update auto-rollback."
    }
  }
}
```

A new feature area gets its own namespace file. Don't grow an unrelated one.

## Add a string to a component

<Steps>
<Step title="Add the key to the JSON file">

Find or create the namespace file under `web/src/locales/en/` and add the key first. The JSON file is the type schema, so a call site cannot use a key that is not there.

</Step>
<Step title="Call t() in the component">

```tsx
import { useTranslation } from 'react-i18next'

export function SomeCard() {
  const { t } = useTranslation('deploys')
  return <p>{t('someFeature.someLabel')}</p>
}
```

For interpolation, use `{{placeholder}}` in the value and pass the data as the second argument: `t('autoRollbackSloBurn.toast.modeSet', { mode: label })`. For strings from more than one namespace, pass an array to `useTranslation` and prefix the non-default key, for example `t('common:actions.copy')`.

</Step>
<Step title="Cover every user-facing string">

That includes `aria-label` values, toast titles and descriptions, tooltip text and `alt` text. Test ids, internal log messages and class names do not belong in a namespace file.

</Step>
<Step title="Check types">

From `web/`, run `npx tsc -b` and `npx eslint src`. A missing or mistyped key fails `tsc`.

</Step>
</Steps>

### Adding a new namespace

Create the JSON file, then register it in two places: add the name to `NAMESPACES` in `web/src/i18n/index.ts` and add its type to `web/src/i18n/resources.ts`.

## How loading works

Each namespace is its own chunk. `web/src/i18n/lazyBackend.ts` imports `../locales/${language}/${namespace}.json` with a fixed directory and extension, which lets Vite split every JSON file out of the main bundle. A namespace downloads the first time a component calls `useTranslation` for it. Only `common`, the default namespace, loads at boot.

Because `useSuspense` is on, a component suspends while its namespace loads. `web/src/main.tsx` wraps the app in one `<Suspense fallback={<PageSpinner />}>`, so this looks like any other route loading state. If you render a component outside that tree, make sure an ancestor has a `Suspense` boundary.

## Type-safe keys

`web/src/i18n/resources.ts` augments i18next's `CustomTypeOptions` with the type of each `en` JSON file:

```ts
declare module 'i18next' {
  interface CustomTypeOptions {
    defaultNS: 'common'
    resources: {
      common: typeof common
      deploys: typeof deploys
      // one entry per namespace
    }
  }
}
```

With that in place, `t('autoRollback.titl')` is a `tsc` error at the call site instead of a silent fallback to the raw key at runtime. This needs `"resolveJsonModule": true` in `tsconfig.app.json`, which is set.

## Testing

Test a translated component with a dedicated `i18next.createInstance()` seeded with the real namespace JSON through `I18nextProvider`, not the app's lazy-loading singleton. Tests then get deterministic, already-loaded translations with no chunk-loading race. `web/src/components/AutoRollbackCard.test.tsx` shows the pattern.

## Languages and fallback

Supported codes live in `SUPPORTED_LANGUAGES` in `web/src/i18n/index.ts`. Users pick one under Settings, Account, Preferences (Language), and the browser language is used when they have not. Regional codes such as `es-MX` resolve to `es`.

A language does not have to translate everything. A missing namespace file loads as empty and a missing key falls back to English, so a partial locale is safe to ship. To add a language:

1. Add its code to `SUPPORTED_LANGUAGES`.
2. Create `web/src/locales/<code>/common.json` (and any other namespaces you translate), with the same keys and `{{placeholders}}` as English.
3. Extend `web/src/i18n/locales.test.ts` for the new file: no extra keys, same placeholders, no em or en dashes.

Spanish currently translates `common` except the `cliConsole` and `dock` sections, which show English.

## Accessibility checks

`web/src/test/pagesA11y.test.tsx` mounts the main pages and the command palette and runs the static checker in `web/src/test/a11y.ts` (names, labels, ARIA references, tabindex, nested controls, headings). `web/src/test/contrast.test.ts` computes WCAG AA contrast for the shared colour tokens in `index.css`, so fix contrast by changing a token, not a component.
